| | |
|---|---|

| **ผลลัพธ์** | PR ของ B ที่เคยมี conflict แก้เสร็จและ merge แล้ว |

## 🎯 เป้าหมาย

เห็น Merge Conflict ของจริง เข้าใจว่ามันเกิดจากอะไร และแก้ได้ด้วยความร่วมมือของสองคน — Conflict **ไม่ใช่ความผิดพลาด** แต่เป็นสัญญาณว่าสองคนต้องคุยกัน

## 📋 ต้องมีก่อนเริ่ม

- ผ่าน [WS2.1](ws-2.1-pr-review.md) (รู้วิธีเปิด PR และ merge)
- ไฟล์ `team-info.md` ใน repo มีบรรทัด `เวลาประชุมทีม: 10:00` (ผู้สอนเตรียมไว้)
- นั่งใกล้กันกับคู่ของคุณ — ขั้นที่ 5 ต้องตัดสินใจร่วมกัน

## 👉 ขั้นตอน

### ขั้นที่ 1 — ทั้งคู่เริ่มจาก `main` ล่าสุดเหมือนกัน

ทั้ง A และ B พิมพ์พร้อมกัน (ชื่อกิ่งต่างกัน):

```bash
git switch main
git pull
```

- **A:** `git switch -c feat/a-meeting-time`
- **B:** `git switch -c feat/b-meeting-time`

### ขั้นที่ 2 — แก้บรรทัดเดียวกัน เป็นค่าคนละค่า

เปิด `team-info.md` แล้วแก้บรรทัด **เวลาประชุมทีม** :

- **A** เปลี่ยนเป็น `เวลาประชุมทีม: 09:00`
- **B** เปลี่ยนเป็น `เวลาประชุมทีม: 13:00`

แล้ว commit และ push (ทำทั้งคู่):

```bash
git add team-info.md
git commit -m "docs(team): set meeting time"
git push -u origin <กิ่งของตัวเอง>
```

💡 ตอนนี้ทั้งสองกิ่งแตกออกจาก `main` จุดเดียวกัน และแก้ **บรรทัดเดียวกัน** — Git จะเลือกให้ไม่ได้

### ขั้นที่ 3 — A เปิด PR และ merge ก่อน

A ทำตาม [WS2.1](ws-2.1-pr-review.md) ขั้นที่ 1–6 จนกิ่งของ A เข้า `main` (ให้ B ช่วย Approve)

### ขั้นที่ 4 — B เปิด PR แล้วเห็น conflict

B เปิด PR ของตัวเอง → GitHub แจ้ง **"This branch has conflicts that must be resolved"** และปุ่ม Merge ใช้ไม่ได้

✅ **ต้องเห็น:** ข้อความ conflict ใน PR ของ B

### ขั้นที่ 5 — B ดึง `main` มารวมในกิ่งตัวเอง แล้วแก้ conflict ใน VS Code (ทำร่วมกับ A)

```bash
git switch feat/b-meeting-time
git pull origin main
```

Git จะบอก `CONFLICT (content): Merge conflict in team-info.md` — เปิดไฟล์ใน VS Code จะเห็น:

```text
<<<<<<< HEAD
เวลาประชุมทีม: 13:00
=======
เวลาประชุมทีม: 09:00
>>>>>>> origin/main
```

- ส่วนบน (`HEAD`) = ฝั่งเรา (B) · ส่วนล่าง (`origin/main`) = ฝั่งที่เพิ่งเข้ามา (ของ A)
- VS Code แสดงปุ่มเหนือบรรทัด: **Accept Current Change** · **Accept Incoming Change** · **Accept Both Changes** · **Compare Changes**

ตกลงกับ A ว่าจะเก็บค่าไหน (หรือเขียนใหม่เป็นค่าที่สาม เช่น `เวลาประชุมทีม: 09:00 และ 13:00`) แล้วคลิกตัวเลือกที่ต้องการ หรือแก้ด้วยมือ

⚠️ ตรวจว่า **เครื่องหมาย `<<<<<<<`, `=======`, `>>>>>>>` หายไปหมดแล้ว**

### ขั้นที่ 6 — ทดสอบ แล้ว commit

```bash
git diff            # ดูผลที่แก้
npm test            # ถ้ามีงานที่เกี่ยวข้อง ให้รัน test ก่อน commit
git add team-info.md
git commit          # ข้อความ merge จะถูกสร้างให้ ใช้ค่านั้นได้เลย
git push
```

### ขั้นที่ 7 — Merge PR ของ B

กลับหน้า PR ของ B → conflict หายไป → ให้ A Approve → **Squash and merge**

✅ **ต้องเห็น:** PR ของ B เป็นสี **Merged** และ `team-info.md` บน `main` เป็นค่าที่ตกลงกัน

## ✅ Checkpoint (ตรวจตัวเอง)

- [ ] คุณเห็นเครื่องหมาย `<<<<<<<` ในไฟล์จริง (ไม่ใช่แค่ในสไลด์)
- [ ] ไม่มีเครื่องหมาย `<<<<<<<` / `=======` / `>>>>>>>` เหลือในไฟล์บน `main`
- [ ] อธิบายเพื่อนได้ว่าทำไมต้องคุยกันก่อนเลือกค่า

## 🔧 ปัญหาที่พบบ่อย

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| ไม่เกิด conflict | A หรือ B แก้ **คนละบรรทัด** หรือ B สร้างกิ่งหลังที่ A merge แล้ว | ให้ B ย้อนไปสร้างกิ่งจาก main ก่อนที่ A merge หรือให้ทั้งคู่แก้บรรทัดเดียวกันอีกรอบ |
| เผลอ commit ทั้งที่ยังมี `<<<<<<<` | ไม่ได้ตรวจไฟล์ก่อน | แก้ไฟล์ใหม่ แล้ว commit อีกครั้ง (อย่า push ถ้ายังไม่ได้ตรวจ) |
| อยากยกเลิกการ merge | ทำไม่ถูกทาง | `git merge --abort` กลับสภาพก่อน `git pull` |
| PR ยังบอกว่า conflict หลัง push | push ไปคนละกิ่ง | ตรวจ `git branch --show-current` ว่าเป็น `feat/b-meeting-time` |

> ทางเลือก: กดปุ่ม **Resolve conflicts** บนหน้า PR เพื่อแก้ในเว็บ — เหมาะกับ conflict เล็ก ๆ แต่การแก้ในเครื่อง (VS Code) ช่วยให้รัน test ก่อน commit ได้

## 🧪 ท้าทายเพิ่ม

- ลองสร้าง conflict ที่ซับซ้อนขึ้น: ให้ A **ลบ** บรรทัดนั้น ส่วน B **แก้** บรรทัดเดียวกัน — Git จะถามอะไร?
- ฝึก `git merge --abort` โดยตั้งใจสร้าง conflict ใหม่แล้วยกเลิก

## 🧑‍🏫 หมายเหตุสำหรับผู้สอน/TA

- ตรวจว่าทุกคู่ได้ **เห็น** conflict จริง ถ้า B merge ก่อน A ได้ ให้สลับบทบาท
- จุดสอน: การเลือก "Accept Both" ต้องอ่านผลลัพธ์เสมอ เพราะบางครั้งทำให้โค้ดผิด (เช่น ซ้ำบรรทัด)
