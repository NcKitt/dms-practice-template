# new-spec — เขียน spec สำหรับงานใหม่ (ยังไม่เขียนโค้ด)

ใช้เมื่อมีงาน/Issue ใหม่ที่ยังไม่มีไฟล์ใน `docs/specs/` · ผลลัพธ์คือ **ไฟล์ spec 1 ไฟล์** เท่านั้น — workflow นี้ **ห้ามแก้หรือสร้างไฟล์โค้ด**

## 1. เก็บข้อมูล

- ถามผู้ใช้: เลข Issue · ชื่อโมดูล/ฟีเจอร์ (`<โมดูล>-<name>`) · ปัญหาของผู้ใช้ที่ต้องแก้
- อ่าน `AGENTS.md`, `docs/memory/decisions.md` และ spec ตัวอย่างใน `docs/specs/` อย่างน้อย 1 ไฟล์
- อ่านโค้ดที่เกี่ยวข้องเท่าที่จำเป็น (ไฟล์ stub ของฟีเจอร์, `src/app.js`, `public/app.js`) เพื่อชี้ตำแหน่งที่จะแก้ให้ถูก

## 2. ร่าง spec

```bash
cp docs/specs/_TEMPLATE.md docs/specs/<โมดูล>-<name>.md
```

เติมครบทั้ง 9 หัวข้อ (ไม่มีให้เขียน "ไม่มี" — ห้ามลบหัวข้อ):

| หัวข้อ | ตรวจตัวเองก่อนส่ง |
|---|---|
| 1 บริบท | บอกได้ว่าผู้ใช้คือใคร ได้ประโยชน์อะไร ต่อยอดจากส่วนไหน |
| 2 Prerequisites | มีสิ่งที่ต้องพร้อมก่อน รวมถึงข้อตกลงกับฟีเจอร์อื่น |
| 3 Contract | API มี Method/Path/Request/Response/Error ครบ · ชื่อฟิลด์ไม่ชนกับ `AGENTS.md` |
| 4 ไฟล์ | อยู่ในช่องของฟีเจอร์ — ถ้าต้องแก้ไฟล์ร่วม ให้ระบุเหตุผลและ "ต้องให้ผู้ดูแลอนุมัติ" |
| 5 ข้อกำหนดสำคัญ | มีอย่างน้อย 1 ข้อด้านความปลอดภัย |
| 6 ห้ามทำเกินสโคป | มีรายการ "ยังไม่ทำในรอบนี้" อย่างน้อย 2 ข้อ |
| 7 Acceptance Criteria | **ทุกข้อมีคำสั่งที่รันได้จริง + ผลที่ต้องเห็น** (มีทั้งกรณีสำเร็จและกรณี error) + lint/test/scope |
| 8 คำถามที่ยังเปิด | สิ่งที่ยังไม่แน่ใจ — อย่าเดาคำตอบเอง |
| 9 Prompt | อ้างชื่อไฟล์ spec นี้ถูกต้อง |

ความยาวไม่เกิน 1–2 หน้า · ใส่โค้ดเฉพาะ "โครง" และ Contract ไม่ใช่ implementation เต็ม

## 3. ตรวจและส่งให้มนุษย์อนุมัติ

- แสดงคำถามในหัวข้อ 8 ให้ผู้ใช้ตอบ แล้วย้ายคำตอบไปไว้ใต้ "ตัดสินแล้ว"
- ตั้ง "สถานะ spec" เป็น `ร่าง`
- เปิด PR เฉพาะไฟล์ spec (หรือแนบลิงก์ในคอมเมนต์ของ Issue) ให้ **Spec Approver** ของทีมตรวจ
- **หยุด** — เริ่มเขียนโค้ดได้เมื่อมนุษย์เปลี่ยนสถานะเป็น `อนุมัติแล้ว` เท่านั้น

## ห้าม

- ห้ามสร้างหรือแก้ไฟล์ใด ๆ นอกจาก `docs/specs/<โมดูล>-<name>.md`
- ห้ามเปลี่ยนชื่อฟิลด์หรือ API ที่ฟีเจอร์อื่นใช้อยู่ — ถ้าจำเป็นให้ใส่ในหัวข้อ 8 แล้วบันทึกการตัดสินใจใน `docs/memory/decisions.md` ผ่าน PR แยก
