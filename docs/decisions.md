# บันทึกการตัดสินใจ (Decision Log)

เหตุผลว่าทำไมโปรเจกต์นี้ถึงเป็นแบบนี้ — ช่วยให้คนและ AI ไม่เสนอรื้อสิ่งที่ตัดสินใจไปแล้ว

**กติกา**
- **เพิ่มต่อท้ายเท่านั้น** ห้ามแก้หรือลบรายการเก่า — ถ้าเปลี่ยนใจ ให้เพิ่มรายการใหม่ที่อ้างถึงรายการเดิม (เช่น "แทนที่ D-003")
- เพิ่มผ่าน Pull Request เท่านั้น · 1 รายการ = 1 เรื่อง · สั้น ๆ พอ
- รูปแบบ: `D-<เลข> — <หัวข้อ>` + วันที่ · บริบท · ตัดสินใจ · ผลที่ตามมา

---

## D-001 — ไม่ใช้ฐานข้อมูล เก็บข้อมูลใน memory หรือไฟล์ JSON
- **วันที่:** 2026-10-21
- **บริบท:** แอปใช้ฝึกกระบวนการทำงานเป็นทีม 1 วัน การติดตั้งฐานข้อมูลบนเครื่องผู้เรียนกินเวลาและพังง่าย
- **ตัดสินใจ:** `src/store.js` เก็บใน memory และบันทึกลงไฟล์ JSON เมื่อตั้ง `DATA_FILE`
- **ผลที่ตามมา:** ข้อมูลหายเมื่อรีสตาร์ทถ้าไม่ตั้ง `DATA_FILE` · ห้ามเสนอเพิ่มฐานข้อมูลในงานฟีเจอร์

## D-002 — แยกฟีเจอร์เป็น "ช่อง" ที่ลงทะเบียนไว้ล่วงหน้า
- **วันที่:** 2026-10-21
- **บริบท:** สมาชิก 4–8 คนต้องทำคนละฟีเจอร์พร้อมกัน ถ้าทุกคนแก้ `src/app.js` หรือ `public/index.html` จะเกิด merge conflict ทุก PR
- **ตัดสินใจ:** ทุกฟีเจอร์มีไฟล์ `src/features/<name>.js` และ `public/features/<name>.js` ที่ลงทะเบียนใน `index.js` ไว้แล้ว ผู้พัฒนาแก้เฉพาะไฟล์ของตัวเอง
- **ผลที่ตามมา:** เพิ่มฟีเจอร์ใหม่ (นอกเหนือ 8 ตัว) ต้องให้ผู้ดูแลเพิ่มช่องในไฟล์ร่วมก่อน

## D-003 — `store.update(id, patch)` แบบทั่วไป
- **วันที่:** 2026-10-21
- **บริบท:** หลายฟีเจอร์ต้องเพิ่มฟิลด์ของตัวเอง (`pinned`, `category`, `acks`) ถ้าแต่ละคนแก้ store เองจะชนกัน
- **ตัดสินใจ:** store มี `update` ที่รับฟิลด์อะไรก็ได้ ยกเว้น `id` และ `createdAt` และเติม `updatedAt` ให้เอง
- **ผลที่ตามมา:** การตรวจความถูกต้องของฟิลด์ใหม่เป็นหน้าที่ของโค้ดฟีเจอร์ ไม่ใช่ store

## D-004 — ฟีเจอร์ที่อ่านข้อมูลของฟีเจอร์อื่นใช้ชื่อฟิลด์ที่ตกลงไว้
- **วันที่:** 2026-10-21
- **บริบท:** ฟีเจอร์ stats ต้องนับ `pinned` (จาก pin) และ `acks` (จาก ack) แต่ทั้งสามทำพร้อมกัน
- **ตัดสินใจ:** ตกลงชื่อและชนิดฟิลด์ไว้ใน spec และ `AGENTS.md` (`pinned: boolean`, `acks: number`, `category: string`) ฟิลด์ที่ยังไม่มีให้ถือเป็นค่าเริ่มต้น (`false`, `0`, `"ทั่วไป"`)
- **ผลที่ตามมา:** แต่ละฟีเจอร์ merge ได้อิสระโดยไม่ต้องรอกัน · ห้ามเปลี่ยนชื่อฟิลด์เหล่านี้

## D-005 — Test ด้วย `node:test` และ lint ด้วย `node --check`
- **วันที่:** 2026-10-21
- **บริบท:** ต้องการให้ `npm ci` เร็วและไม่มี dependency ฝั่ง dev ที่ต้องดูแล
- **ตัดสินใจ:** ใช้ test runner ในตัวของ Node.js และสคริปต์ `scripts/lint.js` ที่ตรวจ syntax
- **ผลที่ตามมา:** ไม่มี ESLint / Jest / supertest — ห้ามติดตั้งเพิ่ม · ใช้ `startTestServer()` แทน supertest

## D-006 — หน้าเว็บเป็น JavaScript ล้วน ไม่มี framework และไม่มี build step
- **วันที่:** 2026-10-21
- **บริบท:** ผู้พัฒนามีพื้นฐานหลากหลาย และ Docker/PM2 ต้อง deploy ได้ทันทีโดยไม่ต้อง build
- **ตัดสินใจ:** `public/` เสิร์ฟเป็นไฟล์ static ฟีเจอร์ต่อเข้าหน้าเว็บผ่าน `init(ctx)`
- **ผลที่ตามมา:** ห้ามเสนอเปลี่ยนเป็น React/Vue/Next.js ในงานฟีเจอร์ · ระบบจริงที่ใช้ Next.js (เช่น UBU BioLink) เป็นอีกโปรเจกต์หนึ่ง

## D-007 — Deploy 2 แบบ: Docker ที่พอร์ต 8080 และ PM2 ที่พอร์ต 3000
- **วันที่:** 2026-10-21
- **บริบท:** ต้องการเทียบสองวิธีบนเครื่องเดียวกันพร้อมกัน
- **ตัดสินใจ:** Docker map `8080:3000` + volume `app-data` · PM2 รันที่ 3000 ข้อมูลอยู่ที่ `data/` · `/api/health` บอก `runtime` และ `version`
- **ผลที่ตามมา:** ตรวจผล deploy ทุกครั้งด้วย `/api/health` (smoke test) · deploy จาก Tag เท่านั้น
